## Core concepts

### Logon types (you will need these)

| Type | Name | Meaning |
|---|---|---|
| 2 | Interactive | Console logon — someone at the machine's own screen |
| 3 | Network | Network logon — accessing a share, authenticating to a service, lateral movement |
| 9 | NewCredentials | Logon with explicit credentials (RunAs) — a second identity inside an existing session |
| 10 | RemoteInteractive | RDP session |

Key insight from the lab: an **interactive (type 2)** logon by a privileged-group member gets a *filtered* token (UAC split-token), while a **network (type 3)** logon carries the *full* token. Attackers don't sit at the console — they come over the network, where their stolen privileges work at full strength. **A type-3 logon by a privileged-group member from an unusual source is the lateral-movement pattern to watch.**

### The 4624 flood — and why it needed tuning

Rule **60106** ("Windows Logon Success", level 3) fires on **every** 4624: Kerberos ticket logons, computer accounts (`WIN-SOCLAB$`), SYSTEM, services, and real people, all in one stream. A human logon drowns in it. The tuning was to split the flood by privilege and by time instead of raising the level on everything:

- **100113** (level 10) — the built-in Administrator (SID `-500`) logged on.
- **100114** (level 5) — a normal human user logged on (machine accounts excluded).
- **100115** (level 12) — any human account logging on **outside business hours**.

Machine logons match none of the three, so 60106 still fires for them: coverage is preserved, the flood is split. See [Event 4624](Event-4624-logon-success/) for the full story, including the DWM and UMFD-2 false positives the tuning surfaced.

### The 4625 rule — and why off-hours matters

Rule **60122** ("Logon Failure", level 5) fires on every failed logon. One failure is a typo; a failure **outside business hours** is a brute-force attempt against a sleeping target. The tuning was one child rule:

- **100116** (level 8) — a failed logon outside business hours (child of 60122, so it suppresses 60122 while it matches).

See [Event 4625](Event-4625-logon-failure/) for the full story, including the proof that a failed RDP logon is always type 3, never type 10.

### Off-hours means UTC, not local time

The `<time>` element in a Wazuh rule is evaluated against the **manager's clock**, and the manager runs on **UTC**. All three off-hours rules (100109, 100115, 100116) use `5 pm - 8 am` UTC, which is **10 PM – 1 PM PKT**. An alert timestamped 01:40 PKT is 20:40 UTC — inside the window. Always convert before concluding a rule "should" or "should not" have fired.

**Verdicts explained:**

- **to verify** — the event has not been generated in the lab yet; no rule ID is claimed for it.

**Notes before generating the remaining 12:**
- **4771 only appears if the Kerberos Authentication Service audit subcategory is enabled** (same lesson as 4688 needing Process Creation — a fresh server has most subcategories at "No Auditing"). Enable it first, or the event is invisible while the account still locks out.
- **4624 fires 60106 on every logon** — filter by account and logon type, or you will drown. The [detection commands](Detection-Commands.md) page has the filters.
- **4672 is the key to the 100113 limit.** 100113 catches the Administrator account only, not privileged-group members. A 4672-correlation rule (4624 chained to a recent 4672 for the same Logon ID) is the follow-up — it needs the 4672 rule ID verified first, which is why 4672 is a priority row.

## MITRE ATT&CK mapping

| Event(s) | Technique | Why |
|---|---|---|
| 4624 | **T1078** — Valid Accounts | A logon with valid credentials — the technique behind every account-takeover and lateral-movement step |
| 4624 (off-hours) | **T1078** — Valid Accounts | Same logon, suspicious timing — off-hours use of valid accounts is the compromise indicator |
| 4625 | **T1110** — Brute Force | Failed logons are the visible symptom of password guessing; a burst against one account is an attack in progress |
| 4625 (off-hours) | **T1110** — Brute Force | Guessing against a sleeping target — the off-hours window is when brute force is least likely to be noticed |
| 4648 | **T1550.002** — Pass the Hash (via NewCredentials) | RunAs with a second set of credentials — legit for admins, the same mechanism attackers use to step up |
| 4672 | **T1078** — Valid Accounts | The admin-logon flag — fires when a privileged account logs on, so it marks the logons that matter most |
| 4769 | **T1558.003** — Kerberoasting | A service ticket request — bulk 4769s with RC4 encryption are ticket theft in progress |
| 4771 | **T1110.001** — Password Guessing | Kerberos pre-auth failures — password guessing that bypasses the 4625 logon record |
| 4776 | **T1550.002** — Pass the Hash | NTLM credential validation — NTLM is weaker than Kerberos, so a spike here can mean hash reuse |

*The 4769 / 4771 / 4776 rows are the expected mappings for the unverified events — confirm them against the fired alert when the event is generated, and correct this table if the alert says otherwise.*
